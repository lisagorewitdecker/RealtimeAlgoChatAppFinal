# Realtime DevAlgoChatApp

DevStudio is a real-time developer collaboration app with shared coding, calls, chat, moderation, and an AI coding assistant.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the Express and Socket.IO API
- `pnpm --filter @workspace/chat-app run dev` — run the Expo client for web or Expo Go
- For a physical-phone debugger check, use **Preview on your phone** and follow [the Expo Go debugger guide](artifacts/chat-app/docs/debugger-check.md).
- `pnpm --filter @workspace/mockup-sandbox run dev` — run the component preview sandbox
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm --filter <package> run typecheck` — typecheck one package; it rebuilds the shared `lib/*` declarations first, so a single-package run reports the same errors as the full run (see Gotchas)
- `pnpm run check:typecheck-scripts` — fails when a package script runs `tsc` against a project without building the shared libraries first; `pnpm run typecheck` runs it before anything else
- `pnpm run build` — typecheck + build all packages
- `pnpm run test` — run every package's suites: the node:test suites, then each package's own `test` script (vitest in the API, jest in the Expo app)
- `pnpm run test:unit` — run only the node:test suites (every `*.test.ts` under a package's `tests/` directory)
- `pnpm run check:test-scripts` — fails when a package holds suites `pnpm run test` cannot reach, and when a `check:*` script any package declares is run by neither `pnpm run test` nor `pnpm run typecheck` — a package's check reaches those chains through the root script that wraps it, so one no root script runs fails too; `pnpm run test` runs it first
- `pnpm run check:browser-requirements` — fails when a Playwright config in `artifacts/api-server/e2e` names no requirement module as its `globalSetup`, or when the suite it runs reads a setting it never declared; `pnpm run test` runs it next
- `pnpm run check:browser-output` — fails when a Playwright config under `artifacts/` writes its failure output inside the repository or keeps it after the run; `pnpm run test` runs it after that
- `pnpm run check:browser-commands` — fails when a Playwright config in the workspace is started by no package script, or when a script names a config that is not there; `pnpm run test` runs it last of the three browser checks
- `pnpm run check:release-suites` — fails when a browser suite is run by no command made before publishing, when the release chain could leave a failing suite unreported, or when a suite declared left out of it is not left out after all; `pnpm run test` runs it after the browser checks
- `pnpm run release:validate` — the command to run before publishing: every browser suite in one `&&` chain (moderation-recovery regressions, launch smoke, auth layout, home-bar clearance, hosted sandbox home bar, banned room, moderation, moderation timeout). It needs a running API and Expo web client, Clerk development keys, `DATABASE_URL`, and both moderator credential pairs; each suite names the settings it signs in with (see Gotchas)
- `pnpm run release:settings` — the chain's first command: names every setting the suites `release:validate` runs declare that this environment does not provide, before the first browser starts, so a missing one is not found partway through the chain. Run it on its own to check an environment without running anything (see Gotchas)
- `pnpm --filter @workspace/api-server run test` — run API unit and Socket.IO tests on their own; needs `DATABASE_URL`, or `DATABASE_TESTS=skip` to finish with no database at all (see Gotchas)
- `pnpm --filter @workspace/chat-app run test` — run Expo app tests on their own
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required services: Replit PostgreSQL, Replit-managed Clerk, Replit AI Integrations for Anthropic, and `SESSION_SECRET`
- Secret: `SENTRY_DSN` — enables production error tracking and the `/api/healthz` uptime monitor in `artifacts/api-server` (see Gotchas)

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5 + Socket.IO
- Client: Expo SDK 54, React Native, React Native Web, Expo Router
- Authentication: Clerk
- AI: Anthropic through Replit AI Integrations
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Gotchas

- Production error monitoring (Sentry) is wired into `artifacts/api-server` and `SENTRY_DSN` is configured as a Replit Secret. It captures uncaught exceptions/rejections, Express request errors, and reports a heartbeat check-in on `/api/healthz` every 5 min (Sentry Crons "missed check-in" = the server is down). Confirm in Sentry's dashboard that the `api-server-healthz` Cron Monitor and the project's issue alert rule actually have notifications turned on — that's dashboard-only config not settable from code.
- `/api/healthz` reports readiness as well as liveness: `{ status: "ok" | "degraded", checks: { <name>: "ok" | "missing" | "malformed" } }`. It stays HTTP 200 while degraded so the deployment startup probe and the Sentry uptime monitor keep measuring liveness only. Required settings are shape-checked once at startup (`artifacts/api-server/src/lib/serverConfig.ts`) and each one is a named check: `clerkWebhookSigningSecret` (`CLERK_WEBHOOK_SIGNING_SECRET`, or `CLERK_WEBHOOK_SIGNING_SECRET_PRODUCTION` in production — `whsec_` plus base64 for 24 bytes), `databaseUrl`, `clerkSecretKey`, `clerkPublishableKey`, `sessionSecret`, and `adminUserIds`. A problem produces one startup error log plus a Sentry issue describing the shape only — never the configured value. Only a missing `DATABASE_URL` stops startup (nothing can be served without it); everything else degrades readiness and keeps the process up.
- Because those startup checks fire only once, the recurring 5-min health check (`artifacts/api-server/src/lib/healthMonitor.ts`) reads the readiness body, not just the 200, so a setting rotated or cleared while the process keeps running is still noticed. A degraded payload raises one Sentry message — `"/api/healthz reports degraded readiness: <check>=<state>"` — then stays quiet for a cooldown (default 60 min, overridable via `HEALTH_DEGRADED_ALERT_COOLDOWN_MS`; longer than the socket cooldowns because the check itself runs every 5 min). Recovery logs `"/api/healthz readiness recovered to ok"` and re-arms the alert immediately, so a later regression is not swallowed by the fixed fault's cooldown.
- Moderator access is an allow-list, not a Clerk role, and it has two sources (`artifacts/api-server/src/lib/accountAccess.ts`): `ADMIN_USER_IDS` — a comma-separated list of Clerk user ids in `.replit` `[userenv.shared]`, so development and production read the same list and production picks up a change at the next publish — plus the `moderators` table, managed from the moderation panel and applied on the next request in both environments without a republish. The environment variable is the bootstrap list: it is checked first, so an empty (or unreadable) table can never lock everyone out, and a read failure of the table degrades to bootstrap-only access instead of erroring an ordinary request. Each grant or revoke and its moderation-history entry are written in one transaction, so a privilege change that cannot be audited is not applied; a moderator listed in `ADMIN_USER_IDS` can only be removed there, and a moderator cannot revoke their own last remaining access. The published database gets the `moderators` table from Replit's publish-time schema diff (the same flow that applies every other schema change to production — never migrate it by hand); until that has happened the panel's moderator endpoints answer 503 with a plain explanation instead of a server error, and bootstrap moderators keep working throughout. The app shows the moderation panel only when `/api/profile` reports `isAdmin: true` — the client never sees either list. Email addresses grant nothing, so the `E2E_MODERATOR_*` credentials only work while their user ids have access.
- Socket.IO auth-failure/disconnect-rate Sentry alerts (`artifacts/api-server/src/lib/socketMonitoring.ts`) ship with conservative default thresholds because the app has no real production traffic yet to baseline against. Once real usage exists, retune without a code change via optional env vars: `SOCKET_AUTH_FAILURE_ALERT_THRESHOLD`/`_WINDOW_MS`/`_COOLDOWN_MS` and `SOCKET_DISCONNECT_ALERT_THRESHOLD`/`_WINDOW_MS`/`_COOLDOWN_MS` (all default if unset or invalid).
- An artifact typechecks a workspace library through that library's generated declarations in `lib/<name>/dist`, not its TypeScript source, because the libraries are composite project references. `dist` is gitignored, so on a fresh checkout it is absent and on an older checkout it can predate a contract change — either way the artifact is measured against the wrong contract and reports errors the full `pnpm run typecheck` does not (`TS6305`, or a misleading "Property 'x' does not exist"). Every artifact's `typecheck` script therefore runs the root `typecheck:libs` (`tsc --build`) first, and each library writes its incremental state to `dist/tsconfig.tsbuildinfo` so that deleting `dist` really does force a rebuild. Invoking `tsc -p` directly instead of the package script skips that step and brings the trap back. Nobody has to remember the convention when adding a package: `scripts/src/checkTypecheckScripts.ts` scans every workspace package for a script that runs `tsc` against a project without the root library build succeeding first (a package-local `tsc --build`, or a build joined with `||` or `;`, does not count), prints the exact command to add and why, and runs as the first step of `pnpm run typecheck` (`pnpm run check:typecheck-scripts` on its own). Its tests are in `scripts/tests/` and run with `pnpm run test:unit`. A library that owns a `tests/` directory needs a second program for it: the project the root `tsc --build` emits that library's declarations from is composite and rooted at `src`, so a file outside `src` cannot join it, and a suite in no program at all is skipped by the full typecheck for where it sits rather than for being right. `lib/browser-test-requirements/tsconfig.tests.json` is that program (`noEmit`, so the suite imports `../src/index.ts` by the file `node --test` really loads), the package's own `typecheck` script runs it, and `pnpm run typecheck` drives `./lib/**` alongside the artifacts and `scripts`.
- `pnpm run test:unit` finds its suites by pattern, not by a list: `scripts/src/runUnitTests.ts` reads the package globs from `pnpm-workspace.yaml` and runs every `*.test.ts` under each package's `tests/` directory with Node's own test runner (`node:test`, TypeScript stripped natively). A suite added to any package's `tests/` directory therefore runs without touching the root package.json — the previous hardcoded file list meant a forgotten path stayed green because nobody ran it. Suites colocated with source belong to their own package's `test` script and are deliberately not matched (`artifacts/api-server/src` is vitest, `artifacts/chat-app/__tests__` is jest, `artifacts/api-server/e2e` is Playwright). Discovery matching nothing at all fails the command, because `node --test` handed a glob with no matches exits 0 reporting zero tests.
- `pnpm run test` is the single command that runs all three runners: `check:test-scripts`, then `test:unit` (node:test), then `pnpm -r --if-present run test`, which drives each package's own script (`vitest run src` in `artifacts/api-server`, `jest` in `artifacts/chat-app`). Each package keeps its own `test` script and the root drives it rather than restating what it runs; the `&&` chain means any runner's failure fails the command. `--if-present` is what lets one command drive three runners and is also the hole it opens: a package holding suites but declaring no `test` script would be skipped in silence. `scripts/src/checkTestScripts.ts` closes it — it fails when a package's test files are reached by neither the root node:test discovery nor its own `test` script, and when the root script drops one of its halves or joins them with `;`/`||`, where an earlier runner's failure goes unreported. For the same reason `artifacts/chat-app` no longer passes `--passWithNoTests`: jest matching nothing is a broken setup, not a pass. The Playwright suites in `artifacts/api-server/e2e` stay out of this command deliberately — they need a live server, a browser, and credentials — and run from `pnpm run release:validate`, the command made before publishing (next bullet). The same check holds the chains themselves together: every `check:*` script the root declares has to be run by `pnpm run test` or `pnpm run typecheck`, reached only through `&&`, because a check dropped from that one long line — in a merge, or in an edit of it — stops running while both commands still report success, which is the failure each of those checks was written to catch. A check lives in the package that holds it and reaches those chains through a root script that wraps it (`check:browser-output` at the root delegates to the `@workspace/scripts` script of the same name), so the rule covers the level below the root too: a `check:*` script any package declares that no full-run command reaches and no root check script runs fails, with the wrapper to add as the fix — otherwise a check added to a package and never wired up is run by nothing and reported by nothing, the same silent green one level down. The checks are read off the manifests rather than listed in the check, so one added later is covered without touching it, and a check that belongs outside the full run is stated in the root manifest's `checksOutsideFullRun` with the reason: `check:debugger` and `check:fonts` are run by the `expo-debugger` and `chat-app-fonts` workflows, one needing the workspace's Nix desktop libraries and the other a full production build. An entry stating no reason, or naming a check no package declares, fails too.
- `pnpm run release:validate` is that single pre-publish command, and it runs every browser suite rather than a chosen one: the offline moderation-recovery regressions, then the launch smoke, auth layout, home-bar clearance, hosted sandbox home-bar, banned room, moderation, and moderation-timeout suites, cheapest first and joined with `&&`, so the first suite that fails fails the command. It calls each package's `test:e2e:*` script rather than restating the Playwright command that script runs, for the same reason the root `test` script drives each package's own runner: two copies of one command drift apart. What used to hold the list together was memory — the chain ran the launch smoke, and the other suites ran when someone remembered their script names — so `scripts/src/checkReleaseSuites.ts` reads the pairing instead. It follows `release:validate` through the scripts it calls and fails when a browser suite is reached by none of them, when a script in that chain joins its parts with `;`/`||` (only the last exit status is reported, so an earlier suite can fail into a green release), or when the root command is renamed out from under the Run & Operate list. A browser suite is a `test:e2e:*` script or any script that starts a Playwright config — discovery is shared with `checkBrowserTestCommands.ts` — so a suite added under another name is held too, and only `<runner> run <script>` counts as reaching one, which is why copying a suite's own Playwright command into the chain reports that suite as unreached. A suite that should not run before publishing is declared in `LEFT_OUT_SUITES` with its reason, which every passing run prints, because a suite left out on purpose and a suite forgotten are the same absence from outside; today that is only `test:e2e:moderation-recovery-live`, which is opt-in against a live Clerk instance and would fail a release run on the opt-in publishing is not meant to give it. That declaration is held both ways: an entry naming a script that is no longer a browser suite fails as a waiver held open, and one the chain does reach fails for describing a run that happens. It runs from `pnpm run test` (`pnpm run check:release-suites` on its own), and its tests are in `scripts/tests/`.
- Every Playwright config in the workspace decides once per run, in `globalSetup`, whether that run may go without the settings its browser checks sign in with; `@workspace/browser-test-requirements` (`lib/browser-test-requirements`) holds each suite's declared settings and the decision itself (`BROWSER_TESTS` unset → run, missing setting → fail naming it, `BROWSER_TESTS=skip` → left out and said out loud). It is a shared library rather than one package's file because the convention is the workspace's: a suite in any package declares itself there and announces through it by package name, the way every other shared library is imported. The config module is the wrong place for that decision: Playwright evaluates it again in every worker process, so a throw there is a worker crash rather than the run's reason for stopping. Nothing used to enforce the wiring, and a config that omits `globalSetup` brings back the quiet pass on the run made before publishing — so `scripts/src/checkBrowserTestRequirements.ts` fails a config that names no `globalSetup`, names one that is not on disk, or names a module that never calls `announceBrowserTests()` from the shared module, and it runs from `pnpm run test` (`pnpm run check:browser-requirements` on its own). It searches the whole workspace, not just the directory those suites live in: a browser config added in another artifact, or above them all, brings the quiet pass back for its own suite, and discovery is shared with the output check below so the two can never disagree about which files are configs. A suite names the config that runs it by its bare name in `artifacts/api-server/e2e` or by its workspace-relative path anywhere else, and its `spec` is read beside that config — where Playwright collects it from — so a suite declared for another package names its config once and keeps its spec short; a bare config name landing on no config in that directory is reported as exactly that, naming the config elsewhere in the tree it meant. Being wired to its own suite settles which list of settings the run is held to, not whether that list covers what the cases read, so the same check reads the other side too: the spec each config runs, the fixtures that spec imports, and the workspace packages those import in turn are scanned for `process.env` reads (`process.env.X`, `process.env["X"]`, and destructuring), and every name found has to appear in that suite's `required` — a case reading `E2E_API_URL` under a suite asking only for `E2E_CHAT_URL` is correctly wired and still fails inside the case. Handing the whole environment to a helper (`assertDevelopment(process.env)`, or the `env: process.env` a call is given in its options) is followed into the function named and on through its own handoffs of that environment, so what it reads counts as the suite's; a handoff the check cannot follow to a declaration it can read is reported rather than passed over, while a function's own parameter default (`env = process.env`) is not a handoff. A suite that really may go without one states it in `optional` with a comment saying why (`MODERATION_TIMEOUT_SUITE`'s record path is handed down by its own verifier; the recovery sweep's `NODE_ENV`, `REPLIT_DEPLOYMENT`, and `ADMIN_USER_IDS` are how it refuses to touch a deployment and which accounts it spares, none of which a development run sets), and the comparison runs both ways, because a declaration nothing reads costs the same wasted trip: a `required` entry nothing the suite runs reads any more fails (it stops the run before any case loads over a setting nobody has to configure) and so does an `optional` entry nothing reads, as a waiver held open. Imports are followed through relative specifiers and into this workspace's own packages, which is what makes `DATABASE_URL` attributable — no spec names it, `@workspace/db` reads it at module scope. A `required`/`optional` list this check cannot read as plain names fails rather than holding the suite to nothing. The launch smoke's URL-shape check lives in its requirement module for the same reason; the moderation timeout regression is the one suite whose requirement module ignores the waiver, because its verifier starts that run deliberately. The decision itself is covered by `lib/browser-test-requirements/tests/browserTestRequirements.test.ts` — in the package that holds the rules, so editing them cannot miss that a suite proves them — and it runs with the other node:test suites from `pnpm run test`. The two moderation-recovery commands run by hand (`e2e:moderation-recover` and `test:e2e:moderation-recovery-live`) are reached by no config and no spec, so they declare themselves in that same module as `CommandRequirement`s and call `requireCommandSettings(<their own declaration>)` before they open the database or reach Clerk: a run missing a setting is refused by name, having created and deleted nothing, where it used to throw partway through a command whose work is deleting accounts and be reported by the command's own catch as the recovery failing. The call answers rather than throws, because those commands catch everything they do so that no provider detail reaches the output. `scripts/src/checkCommandRequirements.ts` holds each declared list to what that command reads — the same both-ways comparison, followed through its imports and its handoffs of the whole environment — and fails a command that never asks, one that asks and drops the answer, one announcing another command's declaration, and a declaration naming a module that is not there. It takes its list of commands from the declarations rather than from the filesystem (a module nobody declared is not a command anything can recognize by name), so declaring none at all fails too; it runs from `pnpm run test` (`pnpm run check:command-requirements` on its own), and its tests are in `scripts/tests/`. Commands deliberately do not name absent `optional` settings the way suites do: an unset `NODE_ENV` and `REPLIT_DEPLOYMENT` are the condition the sweep insists on, so a notice about them would appear on every ordinary development run.
- Each suite deciding for itself is right and stays, but it cannot decide early: `release:validate` chains eight of them, so a missing `E2E_MODERATOR_PASSWORD_2` used to stop the command only when the suite signing in with it was reached — after the recovery regressions, the launch smoke, the auth layout and the banned-room scenario had run — and to name that setting alone, so the next run stopped on the next one. `pnpm run release:settings` (`scripts/src/releaseSettings.ts`) is the chain's first command and makes the same reading once, before the first browser starts: it follows `release:validate` through the scripts it calls the way `checkReleaseSuites.ts` does, takes the `BrowserSuite` whose `config` each of those scripts starts, and hands the union to `decideReleaseSettings` in the shared module, which reports every missing name at once beside the suites that cannot run without each. The names are read off the suites' own declarations — the ones their `globalSetup` decides against — so a suite that starts needing another setting is covered without anything being added here; a second list would be the drift this exists to prevent, and is why the union is computed rather than written down. It is not a `check:*` script: those are forced into `pnpm run test` by `checkTestScripts.ts`, and this reads E2E settings that run's environment has no reason to hold. The waiver reaches it the same way it reaches a suite (`BROWSER_TESTS=skip` leaves the whole chain out and says so, an unrecognized value fails without echoing what it was given), optional settings are left to the suites so that a list of things nothing is wrong with is not printed before the run that could say what they cost, and two things fail besides a missing setting: a chain reaching no browser suite, and a config the chain runs that no declaration names — either would let it clear a run it had not read. Running one suite alone is untouched, since nothing but the chain runs it; its tests are in `scripts/tests/releaseSettings.test.ts` and the decision's own in `lib/browser-test-requirements/tests/`.
- A Playwright failure snapshot copies the page as it stands, sign-in form included, so it can hold a password that was typed into it — a failed sign-in leaves the value in the page until Playwright captures its error context, and masking log messages does not remove it. Playwright writes that output into the package owning the config and keeps it, and every config decides this for itself, so redirecting one `outputDir` protects that suite alone. Every browser config therefore puts `outputDir` under `tmpdir()` from `node:os` and sets `preserveOutput: "never"`; the repository also gitignores `test-results/` so a config that forgets still leaves nothing committable, but the file is written into the working copy all the same. `scripts/src/checkBrowserOutput.ts` fails any Playwright config in the workspace that leaves `outputDir` at the default or preserves output under any setting other than `never` — `"failures-only"` included, since a failure is the run that captured the page. `outputDir` is a per-project setting as well as a run-wide one, so it reads every occurrence in a config, not the first: a project naming its own directory writes there instead, so each one has to be rooted outside the repository on its own, and a run-wide entry is still required because the next project added inherits it. Rooted outside means `tmpdir()` imported from `node:os` (a same-named local helper does not count) or an absolute path elsewhere, optionally through `join`/`resolve`, `+`, or a template. `resolve` is read whole rather than by its first argument, because Node restarts it at any absolute argument: `resolve(tmpdir(), process.cwd(), "test-results")` lands in the working copy and is rejected, and so is any argument after the last absolute one whose destination cannot be established. A `..` climb, an expression this check cannot follow, and a config whose exported object it cannot find all fail rather than passing unexamined. A directory taken from `process.env` fails too — it is chosen after the check has run and can name any place at all, and a temporary-directory fallback says nothing about the run where the variable is set — which is why `playwright.moderation-timeout.config.ts` fixes its own `outputDir` and its verifier no longer passes one in (the JSON report path it does pass is a reporter `outputFile`, not failure output). It runs from `pnpm run test` (`pnpm run check:browser-output` on its own), and its tests are in `scripts/tests/`. Both checks discover configs through `scripts/src/playwrightConfigs.ts`, which walks the workspace from its root (skipping dependency, build, and dot directories) and decides what counts as a Playwright config: the `playwright*` filename, or an `@playwright/test` import beside `defineConfig` — never a bare `*.config.ts`, which out in the workspace belongs to vitest, jest, metro, or vite as often as to Playwright, and never a `.test.`/`.spec.` file, which quotes configs rather than being one. Finding no config at all is still a failure in both, since a check with nothing to check passes exactly like a compliant workspace.
- Three suites in `artifacts/api-server/src` run against the real database (`lib/moderationHistoryPaging.test.ts`, `lib/moderatorStoreDriverError.test.ts`, `lib/profileWrites.test.ts`), and a suite that skips itself reports the same green as one that passed — so whether they may be skipped is decided once per run, not per file. `artifacts/api-server/src/testing/databaseTestRequirement.ts` is vitest's `globalSetup` (`vitest.config.ts`), runs before any suite loads, and prints its decision into the run output: `DATABASE_URL` set → the suites run; unset → the whole run fails naming what to do; `DATABASE_TESTS=skip` → they are left out and the run says so out loud. The waiver holds even when `DATABASE_URL` is set, because those suites insert and delete rows, and an unrecognized `DATABASE_TESTS` value fails rather than being read as `skip`. A waived run finishes on a machine with no connection string at all: `@workspace/db` throws at import when `DATABASE_URL` is missing, so the suites that only needed it to load take a stand-in from `src/testing/databaseDouble.ts` instead — either rows held in memory, which has to be paired with `createDrizzleOperatorModule()` because the engine reads the conditions the drizzle operators build, or a handle that refuses every query so an unexpected one is seen rather than absorbed. The three database-backed suites are skipped rather than mocked, so nothing pretends to have checked what only a database can answer. The rule itself is covered by `src/testing/databaseTestRequirement.test.ts`, the stand-ins by `src/testing/databaseDouble.test.ts`.
- For read-only Sentry event review, use the connected Sentry MCP tools (`findOrganizations`, `findProjects`, and `searchEvents`); the Sentry API-key connector's Management API host is malformed. The verified API project is `lisagorewitdecker-06/react-native`. To count Socket.IO alert events, search the `errors` dataset over a defined period (for example `30d`) with `fields: ["message", "count()"]` and either `message:"Elevated Socket.IO auth-failure rate"` or `message:"Elevated Socket.IO disconnect rate"`. A successful search with no results means no matching alert events were recorded in that period.
